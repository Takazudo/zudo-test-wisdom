## 5つのコアルール

フロントエンドコードに取り組むすべてのAIエージェントは、テスト時にこの5つのルールに従う必要があります：

### ルール1: 最初にテスト計画を宣言する

テストを書いたり検証を実行したりする前に、以下を明示します：

- **何を**テストするか
- **どのレベル**を使用するか
- **なぜ**そのレベルが適切か

```
Test plan:
- Testing: notification banner visibility after CSS fix
- Level: 5 (verify-ui + screenshot)
- Reason: This is a visual bug — the element exists in DOM but
  user reports it's not visible. Need to check computed styles.
```

<Note>

テスト計画を宣言することで、習慣的にレベル1をデフォルトにしてしまうよくある間違いを防げます。意識的なレベル選択を強制します。

</Note>

### ルール2: テストレベルを目標に合わせる

テストレベルは実際に検証しているものと一致しなければなりません：

| 検証している内容 | 最低限使用すべきレベル |
|----------------|---------------------|
| 関数が正しい値を返す | レベル1 |
| コンポーネントが正しい要素をレンダリングする | レベル2 |
| ビルド出力に期待されるコンテンツが含まれる | レベル3 |
| ユーザーフローがブラウザで動作する | レベル4 |
| 何かが視覚的に正しい | レベル5 |
| canvas／フォトエディタなどでL4が書けず、かつL5でも到達できない | レベル6（最終手段、CIには使わない） |

レベル5の問題にレベル1を使用しないでください。テストはパスしますが、バグは残ります。L4が難しいだけ、L5が扱いにくいだけでレベル6に飛ばないでください — L6は下位の*両方のレベル（L4とL5）*が真に実行不可能な場合にのみ正当化されます。

### ルール3: 下位レベルがパスしても問題が解消しない場合はエスカレーションする

テストがパスしたにもかかわらず、ユーザーが問題が修正されていないと言う場合：

1. 同じテストを再実行**しない**
2. ユーザーにキャッシュのクリアを提案**しない**
3. 次のテストレベルにエスカレーション**する**
4. すでにレベル4の場合、レベル5にエスカレーションする
5. レベル5の場合、より深く調査する（祖先要素、スタッキングコンテキストなどをチェック）
6. レベル6（AIベース）には、L4が書けない**かつ**L5がアサーションに届かない場合**のみ**エスカレーションする。L6はレベル5の次のデフォルトのステップでは**ない** — 決定論的なチェックが不可能なcanvas／フォトエディタ系のサーフェスのために確保されています。

<Warning>

**「ブラウザキャッシュをクリアしてください」や「ハードリフレッシュしてください」を解決策として提案しないでください。** ユーザーがまだ壊れていると言う場合、コードがまだ壊れています。キャッシュのせいにするのではなく、実際の原因を調査してください。

</Warning>

### ルール4: UI/CSSはデフォルトでレベル5

以下に関わるタスク：

- CSSの変更
- レイアウトの変更
- 表示の問題
- 視覚的な外観
- レスポンシブデザイン
- 間隔、色、フォント

はレベル5の検証をデフォルトにすべきです。下位レベルはCSSの正しさを検証する構造的能力がありません。

### ルール5: テストしなかったものを報告する

テスト後、ブラインドスポットを明示的に述べます：

```
Verification complete:
- Tested: computed styles confirm banner has display:block,
  opacity:1, and parent has overflow:visible
- Screenshot: banner is visible at top of page
- NOT tested: responsive behavior at mobile breakpoints
- NOT tested: animation transition timing
```

この透明性により、追加のテストが必要かどうかをユーザーが判断できます。

## 4つの実行ルール

階層化されたテストスイートの中で動作するエージェントは、さらにこの4つのルールに従う必要があります。検証アーティファクト、ティアタグ、および昇格ライフサイクルの背景については、[実行ティア](./execution-tiers.mdx)を参照してください。

### ルール6 — 検証テストは自己昇格しない

[ライフサイクル](./test-lifecycle.mdx)に沿い、**継続目的 → レベル → 再実行条件・頻度・予算 → タグ** の順で分類します。既存方針に沿って最初から回帰テストを書く行為は通常の開発であり、新たな個別人間承認を要求しません。一時検証には `@verification` を付け、ゲートに入れません。昇格は明示的な提案とレビュアーの判断を必要とし、エージェントは自分のartifactを自己昇格させません。

提案には継続契約と失敗、適切なレベル、重複・代替証拠、再実行条件と検知時期、決定性、実行可能環境、ティア、予算を記載します。入場判断後に `@verification` を外し、適切なティアタグを付けます。タグなしは入場後のCIセーフを意味し、寿命の自動承認ではありません。

#### 強制：タグが一度も付かなかったスペックを捕まえる

日付・Issue番号・`bugfix`・反復回数は探索のヒントであり、自動的なゲート失敗や除外の根拠にしません。契約と役割を確認します。Issue番号付きのデータ消失回帰テストは、長年greenでも恒久的な検知であり得ます。改名だけでは入場判断になりません。[実行ティア](./execution-tiers.mdx)が暗黙の入場を、[AIスイート精査](../ci-operations/ai-suite-audit.mdx)が全件台帳・全件人手レビューを要求しない調査を扱います。

### ルール7 — 赤いチェックは作者をブロックする

redはrepo設定でrequiredでなくても作者の義務を生みます。既定のgreen-before-merge方針では、open issueと結果報告レーンを持つ正当な `@flaky` 隔離を除き、マージ前に解消します。[一時的なredを許容する開発](../ci-operations/transient-red-development.mdx)の明示的方針があれば、pendingや修復を追跡する局所的redのまま、許可済みの開発マージを進められます。マージ後も失敗の担当は残り、成功とは報告しません。

独立作業の続行条件は、失敗が理解・局所化され、次の作業が依存せず、具体的な担当と確認点のもとで修復を追跡することです。原因不明・横断的失敗、build・runtime基盤の破損、依存作業、原因追跡の困難化、security・データ・公開の危険では影響チェーンを停止します。リリース・デプロイ・公開・移行の必須証拠は外部影響前のゲートとして維持します。全体完了にも統合検証とalert整理が必要です。

マージは統合であり成功の証明ではありません。pending・cancelled・superseded・skipped・deferredは成功ではありません。tested SHA、run・job、証拠、担当、次の行動を記録します。非requiredや古いgreenをred無視の理由にしません。実際の保護・承認要件に従い、このルールからbypass権限を得ることはありません。

[ゲートオペレーターの手順](../test-integrity/deflaking-recipe.mdx)は、自分が書いていないredと非同期統合alertの上限つきtriageを扱います。

### ルール8 — ゲートを不正操作しない

以下のいずれも、リンクされたオープンなissueの参照なしに導入してはなりません：

- 既存のテストへの `test.skip`
- 以前はパスしていたテストへの `@flaky` タグ
- スクリーンショット許容値の緩和（例：ピクセル閾値の引き上げ）
- アサーションの削除

既存のアサーションを編集してゲートをパスさせる場合、テスト差分についてフレッシュコンテキストのレビューが必要です — 元の変更を作成したのと同じセッションで編集を適用してはなりません。

**この要件はアサーションだけでなく、ゲートを定義するファイルにも及びます。** ゲートは、アサーションに一切手を触れずに無力化できます：失敗しているスペックが動かなくなるように `testMatch` パターンを狭める、`--grep-invert` フィルタを追加する、リトライ回数を引き上げる、CIジョブを削除または必須指定から外す、失敗するシナリオがそもそもビルドされないようにフィクスチャ／セットアップスクリプトを編集する、などです。リトライ予算、grepフィルタ、testMatchパターン、ジョブの配線がこのようにゲートを無力化しうるため、**ゲートを定義するファイル**（テストランナー設定、CIワークフロー定義、フィクスチャ／セットアップスクリプト、pre-pushゲートスクリプト）への編集にも同じフレッシュコンテキストのレビューが必要です — 作者のdiff要約を鵜呑みにせず、ゲートファイルを最初から読み直し、元の変更を作成したのと同じセッションで編集を適用してはなりません。

プロジェクトは、テスト戦略ドキュメントに具体的なゲートファイルの一覧を列挙すべきです（例：ランナー設定、フィクスチャセットアップスクリプト、両方のCIワークフローファイル、pre-pushスクリプト）。

ランナーのテストごとのタイムアウトやハング検知用の期限（liveness deadline）は、**アサーションではなくガードレール**です。ハングを診断可能な失敗に変えるためのもので、プロダクトの性質を検証するものではありません。そのため、**通常時と負荷時のレイテンシ分布の実測、または予算内に収める必要のある子プロセスの期限のいずれかから**新しい値を導いたことを示し、オープンなissueへのリンクを付けた引き上げは、アサーションの許容値の緩和には当たりません。ただし、ランナー設定を含むゲートを定義するファイルを編集する場合は、他の変更と同じフレッシュコンテキストのレビューが必須です。デフレーキングレシピの根本原因カタログにある[「すでにイベントに同期している待機の、ハング検知用の固定期限」の項目](../test-integrity/deflaking-recipe.mdx#part-1-—-根本原因カタログ)と、[プロジェクトごとのタイムアウト予算](../tool-patterns/vitest-patterns.mdx#プロジェクトレベルのvitest設定-プロジェクトごとのタイムアウト予算)を参照してください。

```
# Wrong — no issue reference
test.skip('banner renders correctly', () => { ... })

# Wrong — no issue reference
expect(page).toHaveScreenshot({ maxDiffPixels: 500 }) // was 50

# Wrong — gate-defining file edited to make a gate pass, no fresh-context review
testMatch: ['**/*.spec.ts', '!**/banner-*.spec.ts'] // silently excludes failing spec

# Wrong — no derivation, no open issue, no fresh-context review
testTimeout: 30_000 // was 5000

# Right (a) — legitimate skip: a real, deliberate skip, not a flake
// skipped: https://github.com/your-org/your-app/issues/55 — pending backend flag rollout
test.skip('banner renders correctly', () => { ... })

# Right (b) — quarantine: NOT skipped; the test still runs, allowed-to-fail,
# with @flaky in the title, exactly matching the quarantine pipeline's convention
// quarantined: https://github.com/your-org/your-app/issues/55
test('banner renders correctly @flaky', () => { ... })

# Right (c) — project-scoped guardrail; runner config received fresh-context review
test: {
  projects: [
    { extends: true, test: { name: 'unit', include: ['src/**/*.test.ts'] } },
    {
      extends: true,
      test: {
        name: 'scripts',
        include: ['scripts/**/*.test.ts'],
        // 2x the largest 30s child deadline; open issue:
        // https://github.com/your-org/your-app/issues/56
        testTimeout: 60_000,
      },
    },
  ],
}
```

<Note>

(a) のスキップと (b) の隔離は、同じことの言い換えではなく、別々の出口です。`test.skip` と `@flaky` を組み合わせるのは、[ヘビーテスト判断ルール](./heavy-test-decision.mdx#flaky-の隔離パイプライン)が禁じる墓場状態そのものです：スキップされたテストは結果を一切収集しないため、「隔離」されているはずのテストが同時にスキップされていると、どこでも実行されず静かに腐っていきます。(a) は、テストを今は一切実行すべきでない、正当な理由がある場合に使います。(b) — 本来の隔離の慣習 — は、テストの実行と報告は続けつつ、ゲートはブロックさせたくない場合に使います。

</Note>

ルール8をプロジェクト独自のエージェント向けドキュメントに要約して載せる場合は、次の1文を使ってください：

> ゲートを弱める変更にはオープンなissueへのリンクを、ゲートを通すためのアサーション変更とゲートを定義するファイルのあらゆる編集にはフレッシュコンテキストのレビューを必須とし、ランナーのタイムアウトやハング検知用の期限はアサーションではなくガードレールとして扱い、その引き上げは、オープンなissueへのリンクを付け、新しい値を実測のレイテンシ分布（通常時と負荷時の比較）または予算内に収める必要のある子プロセスの期限のいずれかから導いた場合に限って認める。

### ルール9 — スコープを絞った重い検証

変更がヘビーレーンテスト（`@heavy`、`@gpu`、`@interactive`、または `@macos-only` タグの付いたもの）のみでカバーされているコードに触れる場合、作業完了を宣言する前に、関連するヘビースペックを対応可能なホスト上で実行してください。あるいは、ブランチに対してexamワークフローをディスパッチしてください。

どのテストがヘビーレーンとみなされるか、またどのホストが必要かを特定する方法については、[ヘビーテスト判断ルール](./heavy-test-decision.mdx)を参照してください。

```
# Before declaring done — change touches GPU rendering path
$ gh workflow run exam.yml --ref my-feature-branch
# or, if running locally on a capable host:
$ pnpm exec playwright test --grep "@gpu" tests/gpu-render.spec.ts
```

<Warning>

変更されたコードのヘビーレーンカバレッジを実行せずに作業完了を宣言することは、ゲートをスキップすることと同等です。スケジュールされた再検証がそれを検出しますが、その遅延は回帰ウィンドウを生み出します。

</Warning>

#### Confirmチェックを入力が存在する時点で分ける

エージェントワークフローにおける _confirmタスク_ とは、名前が付けられた複数のチェックからなる検証パスです。兄弟タスクの作業がベースブランチにマージされた後で実行し、機能を追加するのではなく、マージ済みの結果を検証する役割を担います。

名前が付けられたすべてのチェックを、その入力が存在する時点によって分類し、以下の両方のリストと担当者をタスク本文に記載してください：

- **マージ済みベース上のローカルチェック — 子エージェントが実行。** 子エージェントが起動された時点ですぐに実行できるチェックです。高速ゲート、ユニットスイート、セルフテスト、フォーマット、型チェックが含まれます。
- **PRまたはCI実行に対するチェック — push後にマネージャーが実行。** ジョブログを読む、必須チェックがgreenであることを確認する、warning annotationを観測する、といったチェックです。すべてのトピックのマージとレビューが完了した後にだけルートPRを開くworktree／epic型のワークフローでは、子エージェントの起動時点にこれらの入力は存在できません。これはそのワークフロー形状の性質であり、子エージェントやCIに普遍的に課される制限ではありません。

両方のリストを明記することで、実行者がCI側のチェックを黙って省略することも、まだ存在し得ないPRを待って停滞することも防げます。

zfb（[Takazudo/zudo-front-builder](https://github.com/Takazudo/zudo-front-builder)、このサイトが走るRustベースのフロントエンドビルドオーケストレーター）には、[Takazudo/zudo-front-builder#2883](https://github.com/Takazudo/zudo-front-builder/issues/2883)という実例があります。このconfirmサブissueでは、5つのローカルコマンドと2つのCIログ確認が求められていました。子エージェントは5つのローカルコマンドをすべて実行し、ルートPRがまだ存在しないという理由とともに、2つのログ確認を後回しとして報告しました。ルートPRが開かれた後、マネージャーがそれらのチェックを実行し、実行URLやdriftのwarning annotationが現れたかどうかを含む観測結果をサブissueに投稿しました。この場で決めた分担に追加コストが生じなかったのは、子エージェントがタスク全体を完了扱いにせず、後回しにしたチェックを明示的に報告したからです。

ルール9に従い、重い検証は、その検証を実行できる担当者、すなわち対応可能なローカルホストまたはCI実行のいずれかに一度だけ割り当ててください。分担を決める基準は入力が存在するかどうかであり、チェックが安価かどうかではありません。confirmタスクがマージ済みベース上で完全なローカルビルドを実行する場合もあります。

## サマリーチェックリスト

修正完了を宣言する前に：

- [ ] テスト前にテスト計画を宣言した
- [ ] テストレベルが変更の性質と一致している
- [ ] テストがパスしたがユーザーが失敗を報告した場合、次のレベルにエスカレーションした
- [ ] CSS/ビジュアルの変更にはレベル5を使用した
- [ ] テストしたものとしなかったものを報告した
- [ ] 新しい検証スペックには `@verification` タグが付いており、自己昇格していない
- [ ] 命名や改名ではなく、継続目的に基づいて入場を判断した
- [ ] redの担当責任を維持し、宣言したマージ・外部影響境界の条件を満たした
- [ ] `test.skip`、`@flaky`、または許容値の緩和はリンクされたissueなしに導入していない
- [ ] 変更がヘビーレーン専用のコードに触れる場合、対応可能なホスト上で関連するヘビースペックを実行した
- [ ] confirmタスクでは、子エージェントが実行可能なローカルチェックと、マネージャーが実行可能なPR／CIチェックを分け、どちらがどちらかを明記した
