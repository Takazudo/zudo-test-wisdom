## レベル3がテストするもの

レベル3のテストは**ビルド出力**を検証します。ソースコードを直接テストする代わりに、ビルドを実行してその結果を検査します。

典型的な対象：

- SSG（静的サイト生成）出力HTML
- テンプレートのレンダリング結果
- バンドラ出力（正しいチャンク、コード分割）
- 生成された設定ファイル
- ビルド時のデータ変換（MDXコンパイル、コンテンツコレクション）

## ツール

| ツール | 役割 |
|-------|------|
| **vitest** | テストランナー、ファイルの読み取りとアサーション |
| **fs/path** | ビルド出力を読むためのNode.jsファイルシステムAPI |
| **cheerio** | HTML出力のパースとクエリ |

## ビルドを先に実行する

レベル3のテストは`dist/`配下のファイルを読み取るだけで、自らビルドをトリガーすることはありません。スイートを実行する前にビルドを実行してください。そうしないと、テストは古い（あるいは存在しない）出力を読むことになります：

```sh
pnpm build && pnpm vitest run --project build
```

`--project build`は、Vitestの設定で名前付きの`build`プロジェクトを定義していれば、それにスコープした実行になります（[Vitestパターン](../tool-patterns/vitest-patterns.mdx)を参照）。名前付きプロジェクトがない場合は、ビルド後に素の`vitest run`を実行しても同じように機能します。

開発者がビルドステップを覚えていることに頼らないようにするには、`globalSetup`でVitest自体に組み込み、素の`vitest run`が常に最新のビルドに対して実行されるようにします：

```typescript
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    globalSetup: ["./tests/build-setup.ts"],
  },
});
```

```typescript
// tests/build-setup.ts
import { execSync } from "node:child_process";

export default function setup() {
  execSync("pnpm build", { stdio: "inherit" });
}
```

<Warning>

**古い**`dist/`に対してレベル3のスイートがグリーンになっても、それは何も証明しません -- それは昨日の出力に対するアサーションであり、あなたが今変更したコードに対してではありません。結果を信頼する前に、必ず再ビルドする（あるいは`globalSetup`を使う）ようにしてください。

</Warning>

## 書き手が複数いるビルド成果物は共有された可変状態

上のWarningは**書き手が1つだけ**であることを前提にしています。ビルドして、それから読む、という前提です。単独で`pnpm build && vitest run`を回している限りこれは成り立ちますが、スイートが読んでいる最中に`dist/`へ書き込めるものが他にあった瞬間、成り立たなくなります。見落とされる書き手はパッケージのライフサイクルフックです。誰もそれをタイプしないからです -- 読み取り専用に見えるコマンドの副作用として発火します。

ビルド成果物は、共有された可変変数と同じように扱ってください。すなわち、**信頼する前にすべての書き手を洗い出す**ことです。

### 書き手をすべて洗い出す

「1回ビルドして何度も読む」という構成に頼る前に、その成果物へ書き込みうるプロセスをすべて列挙します：

- **ライフサイクルフック** -- `prepare`、`prepack`、`prepublishOnly`、`postinstall`。これらを実行するのは人間ではなく、パッケージマネージャです。
- **ウォッチャー** -- `tsup --watch`、`tsc --watch`。開発サーバーが生きている間ずっと書き込み続けます。
- **強制リビルドするスクリプト** -- テストレーン、ワークスペースビルド、ローカルの重量レーンなど、呼ばれるたびに無条件でリビルドするもの。
- **publishの経路** -- `npm pack`、`npm publish`、およびそれらがあなたの代わりに実行するもの。

実在するpnpmモノレポでは、`packages/<pkg>/dist/`に独立した書き手が4つ存在していました -- 上のカテゴリからちょうど1つずつです：

| 書き手 | トリガー |
|---|---|
| `prepare`（`tsup` + `tsc -p tsconfig.build.json`） | `pnpm install`のたびに、無言で |
| `dev:js`（`tsup --watch`）+ `dev:dts`（`tsc --watch`） | `pnpm dev`が生きている間ずっと |
| `pnpm test` / `build:workspace` / ローカルの重量レーン | 無条件の強制リビルド |
| `prepack` + publish | リリース時 |

これらの重なりを機械的に防ぐ仕組みは何もなく、そのプロジェクトは`CLAUDE.md`に書かれた「人間が覚えておくルール」に頼っていました -- *`pnpm dev`が動いている間はテストレーンを実行しないこと*。これが問題の形です。規律だけが防いでいるレースなのです。その結果、実際に起きたことは：

- `--watch`ビルドが`dist/`を消し去り、`.d.ts`を一切再生成しなくなった。`clean`をwatchモードのときだけ無効にすること（`clean: !options.watch`）で修正されました。
- `.d.ts`のウォッチャーが死んだまま放置され、JSは更新され続けるのに`dist/*.d.ts`だけが凍結された。その結果スイートは -- そのパッケージ自身の言葉を借りれば -- 大きく失敗する代わりに、古い型に対して静かに型チェックを通してしまいます。**ソースともはや一致しない成果物に対するグリーンなスイート。原因はビルドし忘れではなく、並行性です。**
- ワークスペースのビルドガードが、自らのドキュメントの記述どおり、フレッシュネスではなく存在だけを確認していた。設計上、古い成果物を受け入れ、鮮度の判断を人間へ差し戻す作りです。

<Warning>

**存在チェックはキャッシュではありません。** `if (!existsSync("dist")) build()`が検出できるのは不在であって、陳腐化ではありません。新しい成果物と古い成果物を区別できないガードはスイートを守っていません -- 守っているのは*成果物が存在しない*ケースだけで、それはガードがなくても気づけた失敗です。

</Warning>

### `--ignore-scripts`はフラグであってプロパティではない

この抽象を具体的にする実際のインシデントがあります。高速ティアのユニットテストがnpmのtarballに含まれるファイル一覧をアサートしており、その呼び出しを読み取り専用にするためにこそ`--ignore-scripts`を渡していました：

```typescript
execFileSync("npm", ["pack", "--dry-run", "--json", "--ignore-scripts"], { cwd: PKG_ROOT });
```

ところが、このフラグが実際に`prepare`を抑止するかどうかは、npmのバージョンに依存していました：

| npm | 同梱される環境 | `--ignore-scripts`があっても`prepare`を実行するか？ |
|---|---|---|
| **10.9.4** | **Node 22 -- CIがピン留めしていたバージョン** | **する**（`prepack`は正しくスキップされる） |
| 11.0.0 | -- | しない |
| 11.9.0 | Node 24 -- ローカル開発で動いていたバージョン | しない |

ローカル開発はNode 24で動いており、packは本当に読み取り専用でした。一方CIはNode 22をピン留めしていたため、同じコマンドが`prepare`を発火させ、それが`clean: true`の`tsup`を実行し、`dist/`をまるごと削除しました。ちょうどそのとき、兄弟のspecがパッケージの`bin/*.mjs`を起動しており、その静的import（`../dist/eject/index.js`）が`ERR_MODULE_NOT_FOUND`で失敗したのです。publishの最中に。リリースは3パッケージのうち1つで停止しました。

<Warning>

**テストの読み取り専用性は、挙動がツールのバージョンによって変わるCLIフラグに依存してはなりません。** `--ignore-scripts`はフラグであってプロパティではありません。ツールが尊重してくれることを期待する引数であって、ファイルシステムが与えてくれる保証ではないのです。同じ理屈は`--dry-run`や`--no-build`、その他あらゆる「意味論が他人のchangelogに書かれているオプトアウト」にも当てはまります。

</Warning>

### はみ出したログ行こそが手がかりだった

このリリース障害の数か月前、CIはすでにビルド自身のログ行 -- `[copy-theme-packs] dist/theme-packs/ OK` -- がpackのJSONより手前に出力され、`JSON.parse`を壊すのを目撃していました。この文字列はビルドの`onSuccess`チェーンからしか出力されません。つまり、読み取り専用のはずのコマンドの内側でライフサイクルがすでに走っていた、という直接の証拠だったのです。そのとき適用された修正は、はみ出した行を読み飛ばす寛容なJSONスキャナでした。症状は隠され、リビルドは走り続け、やがてリリースを落としました。

<Tip>

**JSONの手前に出てくるはみ出したログ行は、フォーマットの癖ではありません -- あなたのビルドが喋っているのです。** 読み取り専用のコマンドが出力するはずのないものを出力したときは、パーサーを寛容にする前に、それを出力したのが誰なのかを突き止めてください。

</Tip>

### ルール: 不変のスナップショットを所有する

**ビルド成果物を読むテストは、その不変のスナップショットを所有しなければなりません。** そしてビルドのフレッシュネスキーは、ソースだけでなく**成果物自身のバイト列**をハッシュしなければなりません。

具体的な形は2つあります。

**形1 -- 成果物のスナップショットを取る。** `npm pack`してtarballを展開するか、`{bin,dist}`をスクラッチディレクトリにコピーし、テストをそのコピーに向けます。そのあとライフサイクルが実際の`dist/`に何をしようと、テストが読んでいるのは誰も手を触れられないバイト列です。

```typescript
// tests/setup/snapshot-package.ts
import { cpSync, mkdtempSync } from "node:fs";
import { join } from "node:path";

const PKG_ROOT = join(__dirname, "../..");

export function snapshotPackage(): string {
  // Inside the package root on purpose -- os.tmpdir() breaks bare-specifier
  // resolution. Prefix is gitignored and removed in teardown.
  const dir = mkdtempSync(join(PKG_ROOT, ".artifact-snapshot-"));
  for (const entry of ["bin", "dist", "package.json"]) {
    cpSync(join(PKG_ROOT, entry), join(dir, entry), { recursive: true });
  }
  return dir;
}
```

<Warning>

**解決に関する注意点。** スナップショットの中に**ベア指定子**でimportするものが含まれる場合、スナップショットは`os.tmpdir()`ではなく*パッケージルートの内側*に置かなければなりません。Nodeはimport元のファイルからディレクトリツリーを遡って`node_modules`を解決します。システムの一時ディレクトリから始めた場合、その遡りはプロジェクトに到達しません。そして、いま追いかけているバグとはまったく無関係な理由で`ERR_MODULE_NOT_FOUND`が出ます。

</Warning>

**形2 -- 入力だけでなく出力もハッシュする。** フレッシュネスマーカーでビルドをキャッシュしているなら、ビルド出力そのものをキーに含めてください。ソースだけから導出したキーは、並行する書き手がマーカーの保証対象である成果物を切り詰めたり、書きかけで放置したり、削除したりしても、依然として一致してしまいます。ソースは変わっていないのですから、マーカーは「もはや記述どおりの状態にない`dist/`」を平然と受け入れるのです。ここで拡張しているフレッシュネスハッシュのレシピは[メカニズム2：変更がなければリビルドをスキップする](../decision-guide/execution-tiers.mdx#メカニズム2変更がなければリビルドをスキップする)を参照してください。

### このガードが正直に主張できること

機械的なガードは役に立ちます。デフォルトレーンのspecを走査し、ビルドやパッケージライフサイクルのコマンド -- `npm|pnpm|yarn`に続く`pack|publish|install|ci|rebuild|run build`、裸の`tsup`など -- を起動しているものを見つけ、明示的な注釈のないspecを失敗させる、というものです。

そして同じ場所でその限界も明記してください。文字列スキャナが捕捉できるのは**起動されたコマンド**だけです。シェルのラッパー、スクリプトのエイリアス、`dist/`配下への直接の`rmSync`/`writeFileSync`は捕捉できません。したがって、機械的に強制されるルールは、それが守ろうとしている不変条件よりも**狭い**のであり、ドキュメントはどちらがどちらなのかを述べなければなりません。ガードが強制するのは「specはビルドコマンドを起動しない」であり、不変条件は「specは成果物に書き込まない」です。

<Danger>

過大に主張するガードは、正直な取り決めよりも悪いものです。実際より強く読めてしまうチェックは、まさにこのセクションが述べてきた失敗を再生産します -- 何も強制していない性質に対する確信、というやつです。

</Danger>

## 例: SSG出力検証

```typescript
// tests/build-output.test.ts
import { describe, it, expect } from "vitest";
import { readFileSync } from "fs";
import { join } from "path";

const DIST = join(__dirname, "../dist");

describe("build output", () => {
  it("generates index.html with correct title", () => {
    const html = readFileSync(join(DIST, "index.html"), "utf-8");
    expect(html).toContain("<title>My Site</title>");
  });

  it("generates sitemap.xml", () => {
    const sitemap = readFileSync(join(DIST, "sitemap.xml"), "utf-8");
    expect(sitemap).toContain("<urlset");
  });

  it("includes all expected pages", () => {
    const pages = ["index.html", "about/index.html", "docs/index.html"];
    for (const page of pages) {
      const content = readFileSync(join(DIST, page), "utf-8");
      // Case-insensitive: toolchains emit the doctype as lowercase `<!doctype html>`.
      expect(content.toLowerCase()).toContain("<!doctype html>");
    }
  });
});
```

## 例: MDXフォーマッターのコントラクトテスト

mdx-formatterの実例パターン：Vitestスイートがフィクスチャファイルで実行して出力を比較することで、Rustフォーマッティングエンジンをテストします。これがレベル1ではなくレベル3である理由は、`format()`がビルドによって生成されたコンパイル済みのネイティブエンジンを駆動する薄いJSラッパーだからです -- テスト対象はそのビルド成果物であり、手書きのTypeScriptロジックではありません（もしフォーマッターがコンパイル済みバックエンドを持たない純粋なJS/TSであれば、この同じ冪等性チェックはレベル1に属することになります）。

```typescript
// tests/format.test.ts
import { describe, it, expect } from "vitest";
import { readFileSync } from "fs";
import { join } from "path";
import { format } from "../src/format";

describe("mdx formatting", () => {
  it("is idempotent", () => {
    const input = readFileSync(join(__dirname, "fixtures/sample.mdx"), "utf-8");
    const first = format(input);
    const second = format(first);
    expect(first).toBe(second);
  });
});
```

<Tip>

**冪等性テスト**はフォーマッターやトランスフォーマーにとって強力な不変条件です：操作を2回適用した結果は、1回適用した結果と同じでなければなりません。

</Tip>

## 出力されたコードを実行する

ここまでの例は、出力を**静的なテキスト**として比較するものでした。ファイルを読み、その内容に対してアサーションを行います。しかし、ビルドツールの中には*実行されるJavaScriptを生成する*ものがあります。ユーザーのハンドラをラップするアダプタ、バンドラのラッパー、スキャフォルダなどです。これらに対しては、文字列の一致チェックではテンプレートが書き出されたことしか証明できません。生成されたコードが実行時に正しく振る舞うことは**証明できない**のです。それを検証するには、成果物を書き出し、インポートし、実際に動かす必要があります。

<Info>

これはレベル3が通常カバーする静的テキストの比較とは別の問いです。後者でのアサーションは「ビルドが正しいファイルを生成したか？」です。一方ここでの問いは「生成されたラッパーは、実行時に入力を内側のハンドラへ確かに引き渡しているか？」というものです。これは*コード生成における引き渡し（threading）*のチェックであり、出力されたモジュールを実行してはじめて答えられます。

</Info>

再利用できるレシピは、**一時ディレクトリ + 動的インポート + envスタブ**です。

1. 合成した内側のバンドルを`mkdtemp`で作ったスクラッチディレクトリに書き出す。
2. 出力ステップ（`emitWorker()`）を実行して、**実際の**`_worker.js`を生成する。
3. 出力されたファイルを`import(pathToFileURL(...))`し、`default.fetch(new Request(...), envStub)`を呼び出す。
4. `(env, ctx)`が正しく引き渡されていることをアサートする。ビルドが出力するラッパーは、`env`をユーザーのハンドラへ渡さなければなりません。
5. `afterEach`でスクラッチディレクトリをクリーンアップする。

```typescript
// tests/emit-worker.test.ts
import { mkdtemp, rm, writeFile } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { pathToFileURL } from "node:url";
import { afterEach, describe, expect, it } from "vitest";
import { emitWorker } from "../src/build.js";

let scratchDirs: string[] = [];

afterEach(async () => {
  for (const d of scratchDirs) {
    await rm(d, { recursive: true, force: true });
  }
  scratchDirs = [];
});

async function scratch(): Promise<string> {
  const d = await mkdtemp(join(tmpdir(), "emit-worker-"));
  scratchDirs.push(d);
  return d;
}

describe("emitWorker threads env/ctx into the inner bundle", () => {
  it("the generated wrapper passes env through to the user handler", async () => {
    const dir = await scratch();

    // A synthetic inner bundle that reads env from the request scope
    // the wrapper sets up (here via AsyncLocalStorage), then echoes it.
    const inputPath = join(dir, "inner.mjs");
    await writeFile(
      inputPath,
      `import { AsyncLocalStorage } from "node:async_hooks";
const STORAGE_KEY = "__adapter_als__";
function getStore() {
  const g = globalThis;
  let als = g[STORAGE_KEY];
  if (!als) { als = new AsyncLocalStorage(); g[STORAGE_KEY] = als; }
  return als.getStore();
}
export default {
  async fetch(request) {
    const store = getStore();
    const env = store?.env ?? {};
    return new Response(
      JSON.stringify({
        token: env.API_KEY ?? null,
        ctxKind: typeof store?.ctx?.waitUntil,
      }),
      { status: 200, headers: { "content-type": "application/json" } },
    );
  },
};
`,
      "utf8",
    );

    // Run the real emit step to produce a real _worker.js.
    const out = await emitWorker({
      inputBundlePath: inputPath,
      outdir: join(dir, "dist"),
    });

    // Import the emitted artifact as ESM and drive it with a
    // synthetic Request + env + ctx -- no wrangler / miniflare needed.
    const worker = (await import(pathToFileURL(out.workerPath).href)) as {
      default: {
        fetch: (
          request: Request,
          env: Record<string, unknown>,
          ctx: { waitUntil: (p: Promise<unknown>) => void },
        ) => Promise<Response>;
      };
    };

    const envStub = { API_KEY: "sk-test-1234" };
    const ctx = { waitUntil: () => {} };
    const request = new Request("https://worker.test/api/foo", { method: "POST" });

    const response = await worker.default.fetch(request, envStub, ctx);
    const body = (await response.json()) as { token: string | null; ctxKind: string };

    // The headline check: env actually reached the inner handler.
    expect(body.token).toBe("sk-test-1234");
    // ctx was threaded too -- its surface matches the runtime shape.
    expect(body.ctxKind).toBe("function");
  });
});
```

<Tip>

内側のバンドルは**合成かつ自己完結**に保ちましょう。ラッパーが使う仕組みの読み取り側（ここでは`globalThis`にキーを置いた`AsyncLocalStorage`）をインライン化します。テストしているのは出力されたラッパーの引き渡しであって、実際のユーザーパッケージではないため、それをバンドルする必要はありません。同じパターンで、ラッパーが中身を見ずに扱う*あらゆる*バインディング（データベースハンドル、シークレット、キューなど）をスタブ化できます。ラッパーは`env`をそのまま保存するだけで、そのメンバーを一切検査しないからです。

</Tip>

<Warning>

それでもこれは完全なランタイムテストではありません。出力されたモジュールをインポートして実行するのは**Node**上であり、本来のターゲットランタイム（Cloudflare Workers、Deno、エッジのサンドボックス）ではありません。ランタイム固有のグローバル、実際のアセットサーバー、プラットフォーム独自のリクエストの挙動はスコープ外です。それらにはレベル4（あるいは実際の`wrangler dev` / miniflareの実行）が必要です。このテストが*証明できる*のは、コード生成が責任を負う契約です。入力を渡し、その入力が引き渡されること、これだけです。

</Warning>

## ブラインドスポット

<Warning>

レベル3のテストはファイルの内容を検証しますが、ランタイム動作は検証しません。以下を検出できません：

- JavaScriptのランタイムエラー
- クライアントサイドのハイドレーション問題（dist の HTML が正しくても、アイランドがハイドレーションするとミスネストしうる -- [ハイドレーションのミスネスト変種](../decision-guide/common-failure-pattern.mdx#ハイドレーションのミスネスト変種)を参照。これはレベル4のハイドレーション後テストでのみ捕捉できる）
- 視覚的レンダリングの問題
- ブラウザAPIとのインタラクション
- ページロード後に動的に読み込まれるコンテンツ

</Warning>

## レベル3を使用するタイミング

| シナリオ | レベル3は適切か？ |
|---------|-----------------|
| SSGページがビルドに含まれていない | はい |
| 出力のHTML構造が誤っている | はい |
| バンドルが大きすぎる/チャンクが不正 | はい |
| ブラウザでのハイドレーションミスマッチ | いいえ -- レベル4を使用 |
| ページがブラウザで空白表示 | いいえ -- レベル4/5を使用 |
| CSSが正しく適用されていない | いいえ -- レベル5を使用 |
